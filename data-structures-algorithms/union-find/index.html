Union Find

A tiny data structure that answers "are these two things connected?" in nearly constant time, using a forest of trees and two clever tricks.

The problem

Suppose you have a bunch of things (people, computers on a network, pixels in an image) and connections keep arriving: Ana knows Ben, Ben knows Caro. At any moment you want to ask: are these two in the same group? Ana and Caro are, through Ben.

Union Find (also called a disjoint-set structure) handles exactly two operations:

  • union(a, b) merges the group containing a with the group containing b.
  • find(x) returns a representative for the group x is in. Every member of that group gets the same answer: find(y) returns that same value for every y in x's group, and a different value for anything outside it. So two things are connected exactly when find(a) == find(b).

It's the engine behind Kruskal's minimum spanning tree algorithm, detecting cycles in graphs, grouping pixels into connected regions, and figuring out which accounts belong to the same person.

The idea: a forest of parent pointers

Each group is stored as a tree, and the tree's root is the group's representative. Every element just remembers one thing, its parent. A root is its own parent.

  • find(x): follow parent pointers up from x until you reach a root.
  • union(a, b): find both roots. If they're different, point one root at the other, and the two trees become one.

The whole structure is a single array, parent, where parent[i] is the parent of element i. Below, you can see both the trees and the array they come from.

Operation log

    Trick 1: union by size

    With naive union, an unlucky order of merges builds a long chain, and find on the bottom element has to walk all of it: O(n) per call.

    The fix is to keep track of each tree's size and always hang the smaller tree under the larger one. An element only gets deeper when its tree is merged into one at least as big, which at least doubles the size of its tree. A tree can only double log₂ n times, so no tree is ever taller than log₂ n. (Union by rank, which compares tree heights instead of sizes, gives the same guarantee.)

    Trick 2: path compression

    find(x) walks from x to the root anyway, so on the way back it can repoint every node on that path directly at the root. The first find pays for the walk, and every later find on those nodes takes a single hop. The trees flatten themselves as you use them.

    How fast is it?

    Versionfind / union
    NaiveO(n) worst case
    Union by sizeO(log n)
    Path compression onlyO(log n) amortized
    Both togetherO(α(n)) amortized

    α(n) is the inverse Ackermann function, which grows so slowly that it's at most 4 for any n that fits in the universe. In practice, union find with both tricks costs a constant amount per operation. Here's the whole thing in Go:

    type UnionFind struct {
	parent []int
	size   []int
}

func NewUnionFind(n int) *UnionFind {
	uf := &UnionFind{parent: make([]int, n), size: make([]int, n)}
	for i := range uf.parent {
		uf.parent[i] = i // everyone starts as their own root
		uf.size[i] = 1
	}
	return uf
}

func (uf *UnionFind) Find(x int) int {
	if uf.parent[x] != x {
		uf.parent[x] = uf.Find(uf.parent[x]) // path compression
	}
	return uf.parent[x]
}

func (uf *UnionFind) Union(a, b int) bool {
	ra, rb := uf.Find(a), uf.Find(b)
	if ra == rb {
		return false // already connected
	}
	if uf.size[ra] < uf.size[rb] {
		ra, rb = rb, ra
	}
	uf.parent[rb] = ra // smaller tree under larger
	uf.size[ra] += uf.size[rb]
	return true
}

    Caveats

    • No splitting. Union find can merge groups but can't take them apart. If connections can be deleted, you need a different structure.
    • Elements are numbers. The array needs indices 0 to n−1. For names or other objects, keep a map from each object to its index.
    • Deep recursion. The recursive find above is elegant, but a long chain could overflow the stack before compression flattens it. Production code often uses an iterative loop instead.
