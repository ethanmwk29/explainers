BFS and DFS

Almost every graph algorithm starts with one of two ways to explore: spread out level by level, or follow one path as deep as it goes. They're the same loop with a different container.

One loop, two containers

To explore a graph from a starting vertex, keep a collection of vertices you've found but not yet explored. Repeatedly take one out, look at its neighbors, and add any you haven't seen before. Mark each vertex the first time you see it so nothing gets explored twice.

  • Breadth-first search (BFS) uses a queue: first in, first out. It explores everything 1 step away, then everything 2 steps away, and so on, in rings spreading outward.
  • Depth-first search (DFS) uses a stack, usually the call stack via recursion: last in, first out. It follows one path as far as it can, then backs up to the most recent fork and tries the next branch.

Both visit every vertex reachable from the start exactly once, and look at every edge a constant number of times, so both take O(V + E) time. What differs is the order, and that order is what makes each one useful for different things.

Why BFS finds shortest paths: the queue only ever holds vertices from two neighboring rings (distance d and d + 1), and it always serves the closer ones first. So the first time BFS reaches a vertex, it's by a path with the fewest possible edges. Follow the search tree edges back to the start to recover that path. This only works when every edge counts the same; with weights, you need Dijkstra.

    
A subtle but important detail: mark a vertex when you add it to the queue, not when you take it out. Otherwise the same vertex can be added many times before it's explored.


    
Grids are graphs too

    
Most graph problems in interviews don't hand you a graph. They hand you a grid: a maze, a map, a board. Each cell is a vertex, and it's connected to its (up to) four neighbors. No adjacency list needed: just compute the neighbors on the fly.

    
    
      
  • Shortest path through a maze is a BFS from the start cell.
    • 
      
  • Counting islands (groups of connected land cells) is "count the connected components": scan the grid, and every time you find land you haven't visited, flood-fill it with a BFS or DFS and add one to the count.
    • 
      
  • Multi-source BFS: put several starting cells in the queue at once (all distance 0). The search spreads from all of them together, which answers questions like "how far is every cell from the nearest exit?" in one pass.

Bipartite graphs: two-coloring with BFS

    
A graph is bipartite if you can split its vertices into two groups so that every edge goes between the groups, never inside one. Think of students and classes, or jobs and workers: edges only connect one kind to the other.

    
To check, run a BFS and color as you go: the start gets one color, its neighbors the other, their neighbors the first again, and so on. BFS's rings make this natural, since each ring gets the opposite color of the one before. If you ever find an edge whose two ends have the same color, the graph isn't bipartite.

    
The underlying fact: a graph is bipartite exactly when it has no cycle of odd length. Going around a cycle, the colors must alternate, which only works out if the cycle has an even number of edges. When the coloring fails, the clashing edge plus the two search-tree paths back to where they meet form an odd cycle: proof that no coloring could ever work.

The code

    
BFS distances, DFS visit order, and the bipartite check in Go. Tested against brute force on thousands of random graphs.


// BFS returns each vertex's distance (in edges) from start, or -1 if it
// can't be reached. adj[v] lists v's neighbours.
func BFS(adj [][]int, start int) []int {
	dist := make([]int, len(adj))
	for i := range dist {
		dist[i] = -1
	}
	dist[start] = 0
	queue := []int{start}
	for len(queue) > 0 {
		v := queue[0]
		queue = queue[1:]
		for _, w := range adj[v] {
			if dist[w] == -1 { // mark w when it's first seen, not when it's dequeued
				dist[w] = dist[v] + 1
				queue = append(queue, w)
			}
		}
	}
	return dist
}

// DFS returns the vertices reachable from start, in the order a depth-first
// search first visits them.
func DFS(adj [][]int, start int) []int {
	visited := make([]bool, len(adj))
	var order []int
	var visit func(v int)
	visit = func(v int) {
		visited[v] = true
		order = append(order, v)
		for _, w := range adj[v] {
			if !visited[w] {
				visit(w)
			}
		}
	}
	visit(start)
	return order
}

// Bipartite tries to 2-color an undirected graph so that every edge joins
// two different colors. It returns the colors (0 or 1) and whether it worked.
func Bipartite(adj [][]int) ([]int, bool) {
	color := make([]int, len(adj))
	for i := range color {
		color[i] = -1
	}
	for s := range adj { // every component gets its own BFS
		if color[s] != -1 {
			continue
		}
		color[s] = 0
		queue := []int{s}
		for len(queue) > 0 {
			v := queue[0]
			queue = queue[1:]
			for _, w := range adj[v] {
				if color[w] == -1 {
					color[w] = 1 - color[v]
					queue = append(queue, w)
				} else if color[w] == color[v] {
					return color, false // an edge inside one color means an odd cycle
				}
			}
		}
	}
	return color, true
}


    
Caveats

    
    
      
  • Recursion depth. Recursive DFS on a long path (say, a 100,000-cell snake in a grid) can overflow the call stack. Use an explicit stack for big inputs.
    • 
      
  • Iterative DFS isn't just BFS with a stack. If you push all neighbors at once and mark on push, you get a valid search, but not the same visiting order as recursive DFS. Algorithms that rely on DFS structure (like low-link) need the recursive behavior, or an explicit stack of "next neighbor to try" positions.
    • 
      
  • Disconnected graphs. A single search only reaches the start's component. To cover everything (for counting components or checking bipartiteness), start a new search from every vertex not yet visited.
    • 
    


    

      
Interview notes

      
How often it comes up: Very high. BFS and DFS are the foundation of most graph questions, and grid problems are among the most common interview questions of any kind.

      
Be ready to:

      
  • Write BFS with a queue (marking on enqueue) and DFS both recursively and with an explicit stack, without hesitating.
  • Treat a grid as a graph: neighbors on the fly, bounds checks, marking visited cells.
  • Recognize "fewest steps" as BFS, and "several starting points at once" as multi-source BFS.
  • Two-color a graph to check bipartiteness, looping over every component.
