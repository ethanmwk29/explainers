Topological sort

Put tasks in an order where every task comes after the things it depends on. Two simple algorithms do it in linear time, and both tell you when it's impossible.

The problem

Some tasks have to happen before others: you put on socks before shoes, compile a library before the program that uses it, take Calculus I before Calculus II. Draw each task as a vertex and each "must come before" as a directed edge u → v. A topological order lists every vertex so that every edge points forward: u always comes before v.

  • It exists exactly when the graph has no directed cycle. A graph like that is called a DAG (directed acyclic graph). If shirt must come before tie, tie before jacket, and jacket before shirt, there's no valid order.
  • There's usually more than one. Socks and shirt don't depend on each other, so either can go first. The order is unique only when every consecutive pair in it is joined by an edge.

Two ways to do it

  • Kahn's algorithm (BFS-style): repeatedly take any task that has nothing left in front of it. Track each vertex's in-degree (how many unfinished prerequisites it has). Start with every vertex at in-degree 0 in a queue; each time you output a vertex, remove its outgoing edges, and any vertex whose in-degree drops to 0 joins the queue.
  • DFS method: run a depth-first search, and add each vertex to a list when it finishes, that is, after everything it points to has finished. Reverse the list at the end. A vertex finishes only after all its dependents, so reversing puts it before all of them.

Both run in O(V + E). Step through each below on the classic "getting dressed" example, then tick Add jacket → shirt to create a cycle and see how each one notices.

How each one detects a cycle

    
    
      
  • Kahn's algorithm gets stuck. Vertices on a cycle each wait on another vertex of the cycle, so their in-degrees never reach 0. If the output has fewer than V vertices, there's a cycle. One subtlety: the leftover vertices aren't all on a cycle. Some are just downstream of one, waiting on something that will never finish (like shoes would be if a cycle ran through pants).
    • 
      
  • DFS finds an edge back into its current path. Vertices are white (unvisited), gray (on the current path, still being explored) or black (finished). An edge to a gray vertex leads back to an ancestor on the current path: a cycle. An edge to a black vertex is fine, since that vertex is already fully explored and can't lead back. Just tracking "visited" isn't enough to tell those apart; see the cycle detection cheat sheet.
    • 
    


    
Kahn or DFS?

    
    
      
  • Kahn's is iterative (no recursion-depth worries), produces the order front to back, and makes it easy to control which valid order you get: use a priority queue instead of a plain queue to always pick, say, the alphabetically smallest available task. Its leftovers tell you which tasks are blocked.
    • 
      
  • DFS is short to write if you already have a DFS, and it's the same machinery as Tarjan's SCC algorithm, which outputs components in reverse topological order.
    • 
    


    
Where it connects

    
    
      
  • Graphs with cycles: collapse each strongly connected component into a single vertex and the result is always a DAG, which you can then sort. That's how dependency tools report "these packages depend on each other in a loop" and still order everything else.
    • 
      
  • Dynamic programming on DAGs: processing vertices in topological order means every vertex's predecessors are done first. That makes longest paths, counting paths, and earliest start times for scheduled tasks one pass each.
    • 
      
  • Everyday uses: build systems (make, Bazel), spreadsheet recalculation, package installers, course planning, and job schedulers all topologically sort a dependency graph.
    • 
    


    
The code

    
Both methods in Go, returning the order and whether one exists. Tested against brute force on thousands of random graphs, including self-loops and duplicate edges.


import "slices"

// TopoSortKahn orders vertices 0..n-1 so that every edge u→v has u before v.
// ok is false if the graph has a cycle (then no such order exists).
func TopoSortKahn(n int, edges [][2]int) (order []int, ok bool) {
	adj := make([][]int, n)
	indegree := make([]int, n)
	for _, e := range edges {
		adj[e[0]] = append(adj[e[0]], e[1])
		indegree[e[1]]++
	}
	var queue []int
	for v := 0; v < n; v++ {
		if indegree[v] == 0 { // nothing has to come before v
			queue = append(queue, v)
		}
	}
	for len(queue) > 0 {
		v := queue[0]
		queue = queue[1:]
		order = append(order, v)
		for _, w := range adj[v] {
			indegree[w]--
			if indegree[w] == 0 {
				queue = append(queue, w)
			}
		}
	}
	return order, len(order) == n // vertices left over means a cycle
}

// TopoSortDFS does the same with a depth-first search: each vertex is added
// after everything it points to, and the list is reversed at the end.
func TopoSortDFS(n int, edges [][2]int) (order []int, ok bool) {
	adj := make([][]int, n)
	for _, e := range edges {
		adj[e[0]] = append(adj[e[0]], e[1])
	}
	const white, gray, black = 0, 1, 2 // unvisited, on the current path, finished
	color := make([]int, n)
	ok = true
	var visit func(v int)
	visit = func(v int) {
		color[v] = gray
		for _, w := range adj[v] {
			if color[w] == gray {
				ok = false // an edge back into the current path: a cycle
			} else if color[w] == white {
				visit(w)
			}
		}
		color[v] = black
		order = append(order, v)
	}
	for v := 0; v < n; v++ {
		if color[v] == white {
			visit(v)
		}
	}
	slices.Reverse(order)
	return order, ok
}
