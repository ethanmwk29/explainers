Strong bridges and dominators

Tarjan's algorithm tells you which vertices of a directed graph can all reach each other. It can't tell you which edges are holding that together. For that you need a different idea: dominators.

What Tarjan can't see

A strong bridge is an edge whose removal breaks strong connectivity: afterwards, some vertex can no longer reach some other vertex. It's the directed version of a bridge.

Compare these two graphs. Tarjan's SCC algorithm gives exactly the same answer for both: one component, {A, B, C}. But their strong bridges are different, so the SCCs alone can't tell you which edges matter.

Even with the shortcut, A → B is still B's only way in, B → C is B's only way out, and C → A is A's only way in. The shortcut itself can go, because the cycle still connects everything.

Split it into two questions

Pick any vertex r as a root. A graph is strongly connected exactly when two things are true:

  1. The root can reach every vertex, and
  2. every vertex can reach the root. (Then any x can get to any y by going through r.)

So an edge is a strong bridge exactly when removing it breaks one of the two. In other words, the edge is unavoidable: either every path from the root to some vertex must use it, or every path from some vertex back to the root must use it. That's the key result behind the fast algorithm (Italiano, Laura & Santaroni, 2012), and it works whichever root you pick.

Dominators

Questions about "every path from the root" are what dominators answer:

  • A vertex d dominates w if every path from the root to w goes through d. The root dominates everything, and every vertex dominates itself.
  • The closest one, the last unavoidable stop before w, is its immediate dominator. Linking each vertex to its immediate dominator gives a tree rooted at the root: the dominator tree.
  • The edge version: an edge u → v is unavoidable for reaching v exactly when u is v's immediate dominator and every other edge into v comes from somewhere you can only reach by passing through v first. Then the first time any path arrives at v, it has to come along u → v.

"Every vertex can reach the root" is the same question on the reversed graph, so you compute dominators twice: once forward and once backward.

Finding them fast

The explorer above uses brute force, which is fine for 8 vertices. The fast version has three steps:

  1. Compute dominators from the root, in the graph and in its reverse. The classic algorithm is Lengauer–Tarjan (1979), by the same Tarjan, and built from similar ingredients: DFS numbering and a low-like "semi-dominator" value. It runs in near-linear time, O(E · α(E, V)). Truly linear-time dominator algorithms came later (Alstrup, Harel, Lauridsen & Thorup, 1999; Buchsbaum et al., 2008). A simpler iterative algorithm by Cooper, Harvey & Kennedy is popular in compilers and is fast in practice.
  2. Test each edge u → v with the rule from the Dominators section: u is v's immediate dominator, and v dominates every other predecessor of v.
  3. Combine the two directions. With linear-time dominators, the whole thing is O(V + E).

Without dominators, you can test each edge by removing it and checking reachability (or rerunning Tarjan). That's O(E · (V + E)) in total.

Graphs that aren't strongly connected

To find the edges that keep every SCC intact, run Tarjan first. Edges between two different SCCs can always be removed: a path between two vertices of the same SCC never leaves it, because any vertex it passed through would be part of that SCC too. Then look for strong bridges inside each SCC separately. Tarjan's algorithm is a preprocessing step here, not the method itself.

All at once is a different story

As with undirected bridges, "which single edges can I remove?" is not "how many can I remove together?" For directed graphs, the all-at-once question (the fewest edges that keep a graph strongly connected) is NP-hard. Keeping just V edges is possible only if the graph has a Hamiltonian cycle. A simple 2-approximation uses the same root idea: keep a tree of paths from the root plus a tree of paths to the root, at most 2(V − 1) edges.

Dominators elsewhere

  • Compilers use dominator trees to find loops and to build SSA form, the representation most optimizers work on.
  • Memory profilers use them too. In a heap snapshot, an object's retained size (how much memory would be freed if it disappeared) is the total size of everything it dominates in the graph of references from the roots.

The code

Strong bridges in Go, using the Cooper–Harvey–Kennedy algorithm for dominators and the edge test above. It's checked against brute force on thousands of random graphs, including graphs with duplicate edges (a doubled edge is never a strong bridge).

// StrongBridges returns the positions (in edges) of every strong bridge of a
// strongly connected directed graph with vertices 0..n-1: the edges whose
// removal would break strong connectivity. edges[i] = [2]int{from, to}.
func StrongBridges(n int, edges [][2]int) []int {
	fwd := unavoidable(n, edges, false) // needed on some path from vertex 0
	rev := unavoidable(n, edges, true)  // needed on some path to vertex 0
	var out []int
	for i := range edges {
		if fwd[i] || rev[i] {
			out = append(out, i)
		}
	}
	return out
}

// unavoidable marks each edge u→v that every path from vertex 0 to v must use
// (in the reversed graph when reverse is true). The test: u is v's immediate
// dominator, there's only one u→v edge, and v dominates its other predecessors,
// so any other way into v has to pass through v first.
func unavoidable(n int, edges [][2]int, reverse bool) []bool {
	adj := make([][]int, n)
	preds := make([][]int, n)
	for _, e := range edges {
		u, v := e[0], e[1]
		if reverse {
			u, v = v, u
		}
		adj[u] = append(adj[u], v)
		preds[v] = append(preds[v], u)
	}
	idom := dominators(adj, preds, 0)
	dominates := func(a, b int) bool { // does a dominate b?
		for b != a && idom[b] != b {
			b = idom[b]
		}
		return b == a
	}

	out := make([]bool, len(edges))
	for i, e := range edges {
		u, v := e[0], e[1]
		if reverse {
			u, v = v, u
		}
		if v == 0 || idom[v] != u {
			continue
		}
		ok, copies := true, 0
		for _, w := range preds[v] {
			if w == u {
				copies++
			} else if !dominates(v, w) {
				ok = false
			}
		}
		out[i] = ok && copies == 1
	}
	return out
}

// dominators computes immediate dominators from root with the iterative
// Cooper–Harvey–Kennedy algorithm. idom[root] == root.
func dominators(adj, preds [][]int, root int) []int {
	n := len(adj)
	var post []int // vertices in DFS postorder
	seen := make([]bool, n)
	var dfs func(int)
	dfs = func(v int) {
		seen[v] = true
		for _, w := range adj[v] {
			if !seen[w] {
				dfs(w)
			}
		}
		post = append(post, v)
	}
	dfs(root)
	num := make([]int, n) // postorder number: higher means earlier in the DFS
	for i, v := range post {
		num[v] = i
	}

	idom := make([]int, n)
	for i := range idom {
		idom[i] = -1
	}
	idom[root] = root
	intersect := func(a, b int) int { // closest common dominator
		for a != b {
			for num[a] < num[b] {
				a = idom[a]
			}
			for num[b] < num[a] {
				b = idom[b]
			}
		}
		return a
	}
	for changed := true; changed; {
		changed = false
		for i := len(post) - 2; i >= 0; i-- { // reverse postorder, skipping the root
			v, best := post[i], -1
			for _, p := range preds[v] {
				if idom[p] == -1 {
					continue // not processed yet
				}
				if best == -1 {
					best = p
				} else {
					best = intersect(p, best)
				}
			}
			if idom[v] != best {
				idom[v], changed = best, true
			}
		}
	}
	return idom
}

Interview notes

How often it comes up: Very low. Essentially never asked in standard software-engineering interviews. Dominator trees do come up in compiler roles.

Be ready to:

  • Give the brute-force answer: for each edge, remove it and check that the root still reaches everyone and everyone still reaches the root (one BFS on the graph, one on the reversed graph). That's O(E · (V + E)).
  • Mention that dominators bring it down to linear time.
  • Use the two-BFS check by itself: it's the standard way to test whether a directed graph is strongly connected.

Practice:

  • No standard LeetCode problem asks for this. The closest is the undirected version, LeetCode 1192 · Critical Connections in a Network.
