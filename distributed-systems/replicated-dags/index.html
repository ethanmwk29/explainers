Replicated DAGs

Two replicas can each make a perfectly valid change to a graph, and merging the two changes can produce a graph that isn't valid. No merge function can fix that. This page shows why and what systems do instead.

A graph as rows

A common way to store a graph in a replicated key-value or wide-column database is one row per vertex and one row per edge. Graph databases built on Cassandra, like JanusGraph, store graphs in roughly this shape, and so do many hand-built "adjacency list" tables:

KeyValue
vertex/A{ name: "Write the spec" }
vertex/B{ name: "Build it" }
edge/A/B{ added by replica 1 }

Each row merges well on its own. The set of edge rows behaves like the add-wins set: if two replicas add edges at the same time, the merge keeps both, and every replica that has seen the same updates ends up with the same edges. That property is called convergence.

Convergence isn't the same as staying valid

Suppose the graph is a list of tasks, and an edge A → B means "A must be done before B". A dependency graph like this has to stay a DAG (directed acyclic graph): if A must come before B and B before A, nothing can ever start.

Now replicate it with no leader. Both replicas have vertices A and B. The network splits.

  • On replica 1, someone adds A → B. Replica 1's graph is still a DAG.
  • On replica 2, someone adds B → A. Replica 2's graph is still a DAG.
  • The network heals. The merged edge set is {A → B, B → A}, which is a cycle.

Each replica checked the rule. The rule held everywhere, right up until the merge. And nothing about the merge was wrong: it converged, exactly as designed. The problem is that "no cycles" is a property of the whole graph, and neither replica could see the whole graph when it said yes.

Invariant confluence

Peter Bailis and his coauthors gave this a name in Coordination Avoidance in Database Systems (VLDB 2015). A rule (an invariant) is invariant confluent if this is always true: start from a valid state, let two replicas each make changes that keep their own copy valid, and the merge of the two copies is valid too.

Their result: an invariant can be enforced without coordination exactly when it's invariant confluent. The example above shows that "acyclic" fails the test. So no CRDT, and no clever merge function, can guarantee all of these at once:

  1. Every replica can accept edge inserts during a partition.
  2. Every accepted edge stays in the graph.
  3. Edges can point in any direction.
  4. The graph never has a cycle.

Every real design gives up one of the four. The sandbox below lets you try each choice.

    The four strategies

    1. Coordinate the risky writes

    Send every edge insert through one place that can see the whole graph, such as a leader or a consensus group. The rest of the system can stay leaderless: vertex writes, property updates, and edge removals are all safe to merge (removing an edge can never create a cycle).

    What you give up: availability. A replica cut off from the leader can't add edges until the partition heals. On the consistency models map, this is the "unavailable" class. It's cheapest when a cycle can only form inside one partition of the data, for example when each project's task graph lives on one shard. A cycle that could cross shards needs a cross-shard transaction.

    2. Make the rule local with a fixed order

    Give every vertex a rank when it's created, and only allow edges from a lower rank to a higher one. Any graph that follows this rule is a DAG: every path climbs in rank, so it can never return to where it started. And each edge can be checked by looking at just that edge, so the check survives merging. "Every edge goes uphill" is invariant confluent even though "no cycles" isn't.

    Git's commit graph works this way. A commit names its parents by their hashes when it's created, so it can only point to commits that already exist, and no older commit can ever point to it. The rank is simply creation order. (A ranked graph like this is already in topological order.)

    What you give up: freedom. Some edges are rejected even when they wouldn't create a cycle. If ranks can be changed later to make room, two concurrent rank changes can bring cycles back, so you'd need one of the other strategies for those.

    3. Keep everything and resolve when reading

    Store every edge insert, each with a timestamp that is unique and the same on every replica (a Lamport timestamp with the replica ID to break ties). To show the graph, replay the edges oldest first and hide any edge that would close a cycle with the edges kept so far. Every replica that has the same edges hides the same ones, so they all show the same DAG.

    Martin Kleppmann and his coauthors used this idea for trees in A highly-available move operation for replicated trees (2021). Moving a folder into its own subfolder on one replica while the reverse happens on another creates a cycle. Their algorithm applies moves in timestamp order, undoing and redoing when an older move arrives late, and skips any move that would create a cycle.

    Which edge loses depends only on the timestamps. In the sandbox's three-edge scenario, replica 1 adds A → B and then B → C, while replica 2 adds C → A. Replica 2's edge carries timestamp 1, older than replica 1's second edge, so B → C is the one hidden, even though replica 1 "got there first" in wall-clock terms.

    What you give up: durability of writes. An edge a user saw accepted can later disappear when an older conflicting edge arrives. Hidden edges should be shown somewhere ("this dependency was dropped because it conflicted with…") or users will think the database lost their data.

    4. Detect and repair

    Accept everything, merge as usual, and look for cycles afterward. A cycle is exactly a strongly connected component with more than one vertex, so Tarjan's algorithm finds them all in one pass. Then fix them: remove an edge automatically, or flag the cycle for a person to resolve. Pat Helland calls this "memories, guesses, and apologies": act on what you know locally, and apologize when it turns out to be wrong.

    If replicas repair on their own, they must all pick the same edge to remove, such as the newest edge on the cycle. Otherwise replica 1 removes A → B, replica 2 removes B → A, and after the next merge both edges are gone.

    What you give up: the invariant itself, for a while. Anything that reads the graph between the merge and the repair must cope with a cycle. A topological sort, for example, has to handle the leftover vertices instead of looping forever.

    Pick three

    Each strategy keeps three of the four properties from earlier:

    A useful rule of thumb: use a fixed order when the domain already has one (versions, time, a hierarchy that only grows downward). Use resolve-when-reading when users need edges in any direction and can live with an occasional "your change was dropped". Coordinate when a dropped write is unacceptable and the graph partitions cleanly.

    Which graph rules are safe?

    The invariant confluence test works for any rule. A rough guide: a check that looks at one row at a time, or only requires that something exists, survives merging. A check that requires something to not exist (a second parent, a duplicate name, a path back) usually doesn't, because the other replica may be creating that thing right now. This matches the CALM theorem (Hellerstein and Alvaro): programs whose conclusions only grow as data arrives never need coordination.

    Resolving when reading, in Go

    Here's strategy 3 as a function of the replicated edge set (with removed edges already filtered out). It's tested on 20,000 random edge sets: the result is always acyclic, every hidden edge really does close a cycle with older kept edges, and shuffling the input never changes the answer.

    // Edge is one replicated edge insert. (Counter, Replica) is a Lamport
// timestamp: unique per insert, and the same on every replica.
type Edge struct {
	From, To string
	Counter  int
	Replica  int
}

// Resolve turns the replicated set of edges into a DAG that every
// replica agrees on. It replays the edges oldest first and hides any
// edge that would close a cycle with the edges kept so far. Two
// replicas holding the same edges, received in any order, get the
// same answer.
func Resolve(edges []Edge) (kept, hidden []Edge) {
	sorted := slices.Clone(edges)
	slices.SortFunc(sorted, func(a, b Edge) int {
		return cmp.Or(cmp.Compare(a.Counter, b.Counter), cmp.Compare(a.Replica, b.Replica))
	})
	out := map[string][]string{}
	for _, e := range sorted {
		if reaches(out, e.To, e.From) {
			hidden = append(hidden, e) // From→To would close a cycle
			continue
		}
		out[e.From] = append(out[e.From], e.To)
		kept = append(kept, e)
	}
	return kept, hidden
}

// reaches reports whether there is a path from src to dst.
func reaches(out map[string][]string, src, dst string) bool {
	seen := map[string]bool{src: true}
	stack := []string{src}
	for len(stack) > 0 {
		v := stack[len(stack)-1]
		stack = stack[:len(stack)-1]
		if v == dst {
			return true
		}
		for _, w := range out[v] {
			if !seen[w] {
				seen[w] = true
				stack = append(stack, w)
			}
		}
	}
	return false
}

    This recomputes from scratch, which costs O(E · (V + E)). That's fine for a few thousand edges. A real system would cache the result and redo only the part after the oldest newly arrived edge, which is what Kleppmann's undo/redo does.

    How this connects to the other explainers

    • The add-wins set is how the edge rows themselves merge, and the vertex-deletion problem above is its add-versus-remove question again.
    • Consistency models: strategy 1 is the price of an "unavailable" model; the others stay available by weakening what a write promises.
    • Vector clocks and Lamport timestamps provide the agreed-on order that strategies 3 and 4 rely on.
    • The cycle detection cheat sheet, Tarjan's SCC algorithm, and topological sort are the tools for the local checks and for detecting cycles after a merge.

    Interview notes

    How often it comes up: Occasionally in system design interviews, usually in its most common form: "how do you keep usernames unique in a multi-region, multi-leader setup?" It's the same problem as the cycle, with a uniqueness rule.

    Be ready to:

    • Explain why convergence doesn't preserve invariants, with a two-replica example like A → B vs. B → A.
    • Name the test (invariant confluence) and sort rules into safe and unsafe: per-row checks and "must exist" rules are safe; uniqueness, limits, and "no path back" are not.
    • Propose a hybrid: keep most writes multi-leader, but route the writes that can break the rule (edge inserts, username claims) through a single home region or a consensus group.
    • Discuss the user-facing cost of the available options: a write that was accepted and later hidden or removed needs to be shown and explained.
