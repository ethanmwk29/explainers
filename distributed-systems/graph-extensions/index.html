Explainers/Distributed Systems

Graph extensions

A base graph, plus extensions that other people build on top of it, each replicated as one versioned unit. Every unit merges cleanly on its own. What breaks are the references between them.

The setup

Two kinds of things are replicated, with no leader:

  • The base: a graph, such as A → B.
  • Extensions: graphs that hang off a vertex in another graph, their anchor. An extension anchored at B might add C and D with B → C → D. Extensions can anchor on other extensions too, so they form chains.

Each graph is replicated atomically: every write replaces the whole graph, never a single row. So a merge can never leave half of an update applied, and each graph is always internally consistent. Plugins on a platform, layers on a map, packages that depend on packages, and overlays on a base configuration all have this shape.

Which version wins

Every write to a graph (creating, updating, deleting, or restoring it) gets the next version number after the one the writer had. When two replicas hold different copies of the same graph, the merge keeps one:

  1. The higher version wins.
  2. At the same version, the later write wins (last writer wins).

Choosing a winner by a fixed order like this is a CRDT: the merge is commutative, associative, and idempotent, so all replicas converge however they sync. A few consequences are worth knowing:

  • Stale writes lose. If one replica writes versions 1, 2 and 3, and another replica that only saw the original later writes its own version 1, version 3 still wins. That's usually what you want: the late writer was working from old data.
  • More edits beat newer edits. The version counts edits along a line of history, not time. A replica that makes three edits offline (version 4) beats a single edit made later somewhere else (version 2). That one edit is lost.
  • Concurrent edits at the same version lose a whole graph. Atomic replacement means last writer wins drops the other writer's entire update, not just the conflicting part.
  • Deletes must be versioned too. A delete is a write of a tombstone at the next version. If it simply removed the graph, a replica that never heard about the delete would send the old graph back during the next sync. Tombstones keep the graph's content, so it can be restored (with yet another version).

What can go wrong

Each graph is valid on its own, so every violation is about a reference: an extension's anchor pointing into another graph. These are all cases where each replica's change was fine locally, and the merge isn't:

Orphaned extensionDeletes the baseCreates an extension anchored on the base
Missing anchorUpdates the base, removing vertex BCreates an extension anchored at B
Broken chainDeletes extension E1Creates an extension anchored on E1

The first four are referential integrity: "every anchor points at something that exists". That rule is safe while things are only added, and unsafe once things can be deleted. They're the focus of the sandbox. The cycle is the replicated DAGs problem again, one level up: the same four strategies apply, with whole graphs in place of single edges. Name collisions are the easiest to remove: qualify every vertex name by its graph (E1/cache), and uniqueness becomes a property of each graph alone, which survives merging. (The sandbox simply hands out unique letters.)

    The strategies

    SQL foreign keys face the same question when the row being referenced is deleted, and offer ON DELETE CASCADE, RESTRICT, and SET NULL. Without a leader, the twist is that the replica doing the delete can only act on the dependents it knows about.

    Dormant (resolve when reading)

    Deleting a graph deletes only that graph. An extension whose anchor can't be found (its parent is deleted, or the vertex is gone, or the parent is itself dormant) is dormant: still stored and still replicated, but not shown. If the anchor comes back (someone restores the base, or a later version brings the vertex back), the extension reappears. Every replica with the same graphs computes the same view, so they agree on what's shown.

    What you give up: a delete leaves its dependents behind as hidden clutter. Something has to show "these extensions are waiting on a missing anchor" so someone can re-anchor or delete them, and storage keeps them until then.

    Cascade (remove wins)

    Deleting a graph or removing a vertex also deletes everything hanging off it. On the replica doing the delete, that covers the dependents it knows about. A concurrent extension it never saw arrives later as an orphan, so the cascade has to run again after merges: any replica that finds an extension without its anchor deletes it.

    What you give up: work nobody chose to delete. An extension created during the partition is deleted by a decision made by someone who didn't know it existed. Restoring the base doesn't bring the cascaded extensions back. They're separate tombstones, and each must be restored by hand, parent first: restoring an extension whose anchor is still missing would just orphan it again, so the sandbox refuses.

    Keep what's referenced (add wins)

    This is the add-wins set's rule applied to references: a delete removes only what the deleter had seen. Deleting a graph also deletes the dependents you can see. A dependent you couldn't see keeps its anchor alive: the deleted graph (or removed vertex) stays visible for it, drawn dashed.

    What you give up: deletes don't always take effect. The person who deleted the base sees it come back after the merge, and the base's content has to be kept (in its tombstone) for as long as anything depends on it.

    Coordinate (restrict)

    One leader handles every write, and it refuses to delete a graph or remove a vertex that some extension still hangs off: delete the extensions first. Because the leader sees every write, nothing can be orphaned. npm adopted a policy like this after the 2016 left-pad incident, when an unpublished package broke thousands of builds that depended on it: a package that other packages depend on can no longer simply be unpublished.

    What you give up: availability. A replica cut off from the leader can't write at all, because even creating an extension must be registered with the leader, or it could be orphaned by a delete the leader approved.

    Not in the sandbox: pin immutable versions

    Instead of replacing a graph, keep every version forever, and have each extension anchor at a specific version (base@v1 / B) or a content hash. A reference to an immutable version can never dangle, so the orphan, missing-anchor and lost-update problems disappear. A "delete" becomes a deprecation that hides the graph from new extensions. Go modules, Nix, and Git all work like this. The cost moves somewhere else: when the base publishes v2, each extension still points at v1 until it is deliberately moved, which is a migration that can fail if v2 dropped its anchor.

    Dormant is the default to reach for, for the same reason the replicated DAGs page prefers hiding to deleting: deciding what's hidden is a pure function of the stored graphs, so it can always be recomputed when more information arrives, and nothing anyone wrote is destroyed by a guess. Pair it with pinned versions if the base changes often.

    The model in Go

    Here are the two pieces: the version rule used to merge, and the dormant rule for what's shown. Both are tested against a brute-force version of their definitions on tens of thousands of random cases, including anchors that point at themselves or in loops.

    // Graph is one replicated, versioned graph: the base or an extension.
// Every write (an update, a delete, a restore) replaces the whole graph.
type Graph struct {
	ID       string
	Version  int
	Time     int64 // when it was written; breaks ties within a version
	Replica  int   // last-resort tie-breaker
	Deleted  bool  // a tombstone: deletes are versioned writes too
	Vertices []string
	// The vertex this graph hangs off, in another graph.
	// Empty for the base.
	AnchorGraph, AnchorVertex string
}

// Beats reports whether a wins over b: the higher version wins, and
// within the same version, the later write wins.
func Beats(a, b Graph) bool {
	if a.Version != b.Version {
		return a.Version > b.Version
	}
	if a.Time != b.Time {
		return a.Time > b.Time
	}
	return a.Replica > b.Replica
}

// Merge combines two replicas' states graph by graph. Picking a winner
// by a fixed order is commutative, associative, and idempotent, so all
// replicas converge no matter how often or in what order they sync.
func Merge(x, y map[string]Graph) map[string]Graph {
	out := make(map[string]Graph, len(x))
	for id, g := range x {
		out[id] = g
	}
	for id, g := range y {
		if cur, ok := out[id]; !ok || Beats(g, cur) {
			out[id] = g
		}
	}
	return out
}

// Visible reports which graphs to show. A graph is shown if it isn't
// deleted and its anchor vertex is in a graph that is itself shown.
// Every other graph is dormant: still stored, but hidden until its
// anchor comes back.
func Visible(graphs map[string]Graph) map[string]bool {
	const (
		unknown = iota
		visiting
		yes
		no
	)
	state := map[string]int{}
	var visit func(id string) bool
	visit = func(id string) bool {
		switch state[id] {
		case yes:
			return true
		case no, visiting: // visiting: an anchor loop can't be grounded
			return false
		}
		state[id] = visiting
		g, ok := graphs[id]
		show := ok && !g.Deleted
		if show && g.AnchorGraph != "" {
			show = visit(g.AnchorGraph) &&
				slices.Contains(graphs[g.AnchorGraph].Vertices, g.AnchorVertex)
		}
		state[id] = no
		if show {
			state[id] = yes
		}
		return show
	}
	out := map[string]bool{}
	for id := range graphs {
		if visit(id) {
			out[id] = true
		}
	}
	return out
}

    How this connects to the other explainers

    • Replicated DAGs covers invariant confluence, the test for which rules can survive a merge. "Every anchor exists" passes while things are only added, and fails once they can be deleted.
    • The add-wins set is the "keep what's referenced" rule in its simplest form: a remove only removes what the remover saw.
    • Vector clocks are the precise tool for what the version number approximates: telling a write that saw another apart from one that's concurrent with it. With a vector clock per graph, you could keep both concurrent versions (as siblings) instead of dropping one.
    • Consistency models: the coordinate strategy is what an "unavailable" model costs.

    Interview notes

    How often it comes up: Occasionally in system design interviews, usually disguised: "a user deletes a folder while someone else uploads a file into it", "a service deletes a record other services reference", or "design a plugin marketplace".

    Be ready to:

    • Name the options for a deleted parent (cascade, restrict, hide the children, keep the parent alive) and say which ones need coordination.
    • Explain why a cascade can't reach dependents the deleting replica hasn't seen, and what you do when they show up later.
    • Explain tombstones: why a delete has to be a versioned write, and when a tombstone can finally be dropped (once every replica has seen it).
    • Discuss version numbers versus timestamps for last writer wins, including the "three offline edits beat one newer edit" behavior.
    • Suggest immutable, versioned references (like package versions or content hashes) to make dangling references impossible.
