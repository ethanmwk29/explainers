Scuttlebutt: gossip that keeps up

Gossip protocols spread state through a cluster with no coordinator, but they can only carry so much. Scuttlebutt is a way to spend that limited bandwidth on the updates that matter, plus a way to stop participants from producing more than the cluster can carry.

Based on "Efficient Reconciliation and Flow Control for Anti-Entropy Protocols" by Robbert van Renesse, Dan Dumitriu, Valient Gough and Chris Thomas (Amazon.com; LADIS 2008).

Gossip, briefly

Imagine a cluster of machines, called participants, where each one publishes some state about itself: its load, its health, which data it holds. Everyone wants an up-to-date copy of everyone else's state.

In an anti-entropy gossip protocol, every participant periodically picks a random peer and the two reconcile: each sends the other whatever newer information it has. Updates spread like an epidemic, reaching all N participants in roughly log N rounds. Lost messages and crashed participants barely slow it down.

The catch: gossip has a capacity

To keep gossip predictable and non-invasive, the designer fixes both how often participants gossip and how big a gossip message can be, for example one UDP packet. The paper calls that limit the MTU: a gossip message carries at most mtu updates, called deltas.

That makes the gossip channel a pipe with a fixed width. If participants produce updates faster than the pipe can carry them, a backlog builds up and, in the paper's words, latency "may grow without bounds." The paper makes two contributions for this situation:

  • Scuttlebutt reconciliation: a cheap way to work out what to send, and which deltas to prioritize when they don't all fit.
  • Flow control: a decentralized way for participants to slow down so the backlog never builds up in the first place.

The model

Each participant owns a set of keys, and only the owner may update its own keys. Everyone else's copies change only through gossip. Every value carries a version number, and when two copies of the same key meet, the higher version wins.

Scuttlebutt adds one rule: when a participant updates a key, the new version must be higher than any version it has used before, for any of its keys. In effect, each participant has a single counter, and every update it makes takes the next number. No two of its keys ever share a version.

Scuttlebutt in two steps

When participants p and q gossip:

  1. Swap digests. Each sends a digest: for every participant r, the highest version it holds for any of r's keys. That's one number per participant, no matter how many keys each one has.
  2. Send what's newer. For each participant r, p sends every entry it holds for r whose version is higher than q's maximum for r, and q does the same in return.

Compare that with precise reconciliation, which sends exactly the entries where the peer's copy is older, key by key. To do that, the participants need to exchange a version for every key of every participant, which can be a lot of data, or compute hashes, which costs CPU. Scuttlebutt's digest is tiny by comparison.

The one constraint: send in version order

When everything doesn't fit in one message, Scuttlebutt can't send an arbitrary subset. If it leaves out a delta for participant r, it must also leave out every delta for r with a higher version. In other words, each participant's deltas go out lowest version first.

That's what makes one number per participant enough. It guarantees that, for every key of r, a peer either already has r's current value, or r's current version for that key is higher than the peer's maximum for r, so the next digest will ask for it. There are never gaps hiding below the maximum. As a result, if a peer's maximum for r equals r's own maximum, the peer's copy of r is exactly up to date.

A surprising property

Step 6 of the tour shows something odd. P and Q have the same maximum for R, so they exchange nothing about R, even though Q holds newer versions of b and c than P does. A Scuttlebutt exchange doesn't try to remove every difference between two participants, even when there's room in the message.

That turns out to be a feature. Q's newer copies are already obsolete: R has since moved on to even newer versions. Sending them would just mean reconciling those keys again later. Skipping them leaves room in the message for deltas that are actually current.

What consistency does Scuttlebutt give you?

Here's how Scuttlebutt lines up against Jepsen's map of consistency models. Treat each participant as one of Jepsen's processes: it reads from its own local copy and writes only its own keys. Scuttlebutt has no transactions, so only the single-object branch of the map applies (linearizable down through the session guarantees). The multi-object models, like serializability, aren't on the table.

The MTU is what breaks per-owner ordering

If every exchange carried all of an owner's missing deltas, a peer's copy of that owner's state would always be a state the owner actually had at some point, and it would only move forward. Each owner's writes would then be seen in order, and you'd get PRAM. Truncation breaks this, because a truncated message carries only the oldest of the owner's current entries, and intermediate versions that have been overwritten are never sent. I checked this with the simulation on this page. With unlimited messages, 0 of 432,000 sampled copies were states their owner never had. With an MTU of 2, 7,395 were.

In practice

  • Treat gossiped state as eventually consistent hints. That suits what Scuttlebutt is usually used for, like membership, health, load and configuration, where slightly stale is fine.
  • Don't rely on two keys being in sync, even for one owner. A peer can see one key's update without the other's. If values must change together, put them in a single key, so they share one version.
  • Need causal consistency? Attach dependencies to updates (for example, version vectors) and hold back an update until everything it depends on has arrived. That costs more metadata, and readers have to stick to one participant.
  • Availability: reads never wait, and every participant can always update its own keys, even during a partition. But only P can update P's keys.

Choosing what fits

When the deltas don't fit in one message, something has to pick which ones go first. Any ordering works as long as each participant's deltas stay in version order, but the choice matters a lot for performance. The paper compares four:

  • scuttle-breadth tries to be fair: it includes deltas from as many different participants as possible, taking each participant's lowest version first, then each one's second-lowest, and so on. Ties go to a fresh random order of participants for every message, to avoid long-term bias.
  • scuttle-depth prioritizes whoever is most behind: the participants with the most outstanding deltas go first, in version order, again with random tie-breaking. The authors call it "the best we encountered from various trials."
  • precise-newest (a baseline) uses precise reconciliation and sends the most recent updates first. It can starve older updates, so they never get a chance to spread.
  • precise-oldest (a baseline) sends the most out-of-date deltas first.

Both precise orderings would need synchronized clocks and timestamps on every update to implement for real. The simulation below can cheat and use its own clock.

It follows the schedule from the paper (rate 1, doubled at round 25, restored at round 75, stopped at round 120), scaled down from the paper's 128 participants and 64 keys.

The pattern matches the paper's results. Under overload, precise-newest keeps the fewest out-of-date copies but has the worst maximum staleness, because some old updates starve. precise-oldest keeps staleness lower but accumulates the most out-of-date copies, so it recovers slowly. scuttle-breadth is disappointing, which shows how much the ordering matters. scuttle-depth scores well on both metrics. In every variant, once updates stop, the cluster converges. As the paper puts it, though, "no matter how good the reconciliation protocol, overload remains a problem."

Flow control

Good reconciliation makes the best of a backlog. Flow control prevents one. The goal is for each participant to find, on its own, the fastest rate at which it can publish updates without creating a backlog, while sharing capacity fairly among everyone who wants to publish. There's no central coordinator, so it has to be built from local decisions.

Each participant p has a desired rate ρp (how fast updates become available) and a maximum rate τp that it never exceeds and adjusts over time. Two mechanisms adjust τ:

1. Local adaptation (AIMD)

This works like TCP's congestion control: additive increase, multiplicative decrease. The overflow signal is a gossip message that's completely full. A single full message isn't a reliable signal, so the rule looks for a streak:

  • If, for φ1 exchanges in a row, either delta set (sent or received) is larger than mtu: τp = α · τp.
  • If, for φ2 exchanges in a row, both delta sets are smaller than mtu: τp = min(τp + β, mtu).

The paper's experiments use φ1 = φ2 = 3, α = 0.75 and β = 0.2.

2. Spreading capacity fairly

AIMD alone can be unfair: some participants back off while others speed up. To fix that, participants piggyback their ρ and τ on gossip and rebalance with every exchange. Let T = τp + τq:

  • Both fit (ρp + ρq ≤ T): each gets its desired rate plus half the spare capacity, τp = ρp + (T − ρp − ρq)/2, and likewise for q.
  • Both want more than half (ρp ≥ T/2 and ρq ≥ T/2): split evenly, τp = τq = T/2.
  • One wants less than half (say ρp < T/2): p gets what it wants, τp = ρp, and q gets the rest, τq = T − ρp.

In all three cases τp + τq stays the same. No capacity is created or lost, it just gets shared more evenly.

See it work

Two clusters, both using scuttle-depth, where every participant wants to publish 8 updates per round, far more than the network can carry. One cluster has flow control and one doesn't. Let it run, then drop the MTU partway through, like the paper's experiment that halves it to simulate a sudden network load increase.

Without flow control, staleness climbs steadily: the backlog never drains. With it, each participant's rate creeps up until the messages start overflowing, then settles near what the network can actually carry. When the MTU drops, the rate quickly falls to a level the smaller messages can support, and staleness stays bounded. The paper reports the same behaviour, and notes that the combination of Scuttlebutt and flow control "appears particularly effective."

The code

Here's a Scuttlebutt participant in Go, with digests, version-ordered deltas and scuttle-depth prioritization. To keep it short, it leaves out the network layer, flow control and failure handling.

import (
	"math/rand"
	"sort"
)

// Delta is one (participant, key, value, version) tuple sent during gossip.
type Delta struct {
	Owner   string
	Key     string
	Value   string
	Version int
}

type entry struct {
	value   string
	version int
}

// Node is one participant. It owns its own keys and holds a replica of
// every other participant's keys.
type Node struct {
	id    string
	state map[string]map[string]entry // owner -> key -> entry
	max   map[string]int              // owner -> highest version held
}

func NewNode(id string) *Node {
	return &Node{id: id, state: map[string]map[string]entry{}, max: map[string]int{}}
}

// Set updates one of this node's own keys. The new version is higher than
// any version the node has used before, for any key.
func (n *Node) Set(key, value string) {
	n.put(n.id, key, entry{value, n.max[n.id] + 1})
}

func (n *Node) put(owner, key string, e entry) {
	if n.state[owner] == nil {
		n.state[owner] = map[string]entry{}
	}
	if e.version > n.state[owner][key].version {
		n.state[owner][key] = e
	}
	if e.version > n.max[owner] {
		n.max[owner] = e.version
	}
}

// Digest is the highest version this node holds for each participant.
func (n *Node) Digest() map[string]int {
	d := make(map[string]int, len(n.max))
	for owner, v := range n.max {
		d[owner] = v
	}
	return d
}

// DeltasFor returns the entries a peer with the given digest is missing:
// at most mtu of them, chosen with the scuttle-depth ordering.
func (n *Node) DeltasFor(digest map[string]int, mtu int) []Delta {
	byOwner := map[string][]Delta{}
	for owner, keys := range n.state {
		for key, e := range keys {
			if e.version > digest[owner] {
				byOwner[owner] = append(byOwner[owner], Delta{owner, key, e.value, e.version})
			}
		}
	}

	owners := make([]string, 0, len(byOwner))
	for owner, ds := range byOwner {
		// Within a participant, always send in version order.
		sort.Slice(ds, func(i, j int) bool { return ds[i].Version < ds[j].Version })
		owners = append(owners, owner)
	}
	// scuttle-depth: participants with the most outstanding deltas go first,
	// with ties broken randomly.
	rand.Shuffle(len(owners), func(i, j int) { owners[i], owners[j] = owners[j], owners[i] })
	sort.SliceStable(owners, func(i, j int) bool {
		return len(byOwner[owners[i]]) > len(byOwner[owners[j]])
	})

	var out []Delta
	for _, owner := range owners {
		for _, d := range byOwner[owner] {
			if len(out) == mtu {
				return out
			}
			out = append(out, d)
		}
	}
	return out
}

// Apply merges received deltas, keeping whichever version is higher.
func (n *Node) Apply(deltas []Delta) {
	for _, d := range deltas {
		n.put(d.Owner, d.Key, entry{d.Value, d.Version})
	}
}

// Gossip runs one exchange between a and b: swap digests, then send each
// other what's missing, limited to mtu deltas per message.
func Gossip(a, b *Node, mtu int) {
	da, db := a.Digest(), b.Digest()
	toB, toA := a.DeltasFor(db, mtu), b.DeltasFor(da, mtu)
	b.Apply(toB)
	a.Apply(toA)
}

Caveats

  • Digests grow with the cluster. A digest has one entry per participant, which might not fit in a single message in a very large system. The paper suggests organizing large systems hierarchically, splitting the digest across several messages, or sending a random subset of participants each time, which still works but slows propagation.
  • Deltas aren't all the same size. The model counts deltas, but real ones vary in size. The paper notes this "is not a major complication."
  • Simulation, not reproduction. The charts above come from a small simulation written for this page (32 participants and 16 keys, against the paper's 128 and 64), so the shapes match the paper's results, but the numbers don't. "Max staleness" here means how long the oldest out-of-date copy has been out of date.
  • Where you'll see it. The same "digest of max versions, then send what's newer" pattern shows up in production gossip systems, such as the cluster-membership gossip in Apache Cassandra.
