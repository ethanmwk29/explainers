The add-wins set

Two copies of a set are edited offline, then synced. How do they end up agreeing, with no server to break ties?

The problem

Picture a shared shopping list on your phone and your laptop. Both devices can edit it offline, and they sync whenever they get a connection. Most of the time that's easy: if you add milk on one device, the other device adds milk too.

The trouble is concurrent edits. Suppose that while the devices are disconnected, you remove milk on the laptop and someone adds milk on the phone. When they sync, should milk be on the list or not?

A CRDT (conflict-free replicated data type) is a data structure designed so that replicas can always merge, in any order and any number of times, and still end up in the same state. The add-wins set (also called an observed-remove set or OR-Set) answers the milk question with a simple rule:

If an add and a remove of the same element happen concurrently, the add wins.

The trick: tag every add

A plain set can't tell "milk was removed" apart from "milk was never added." So the add-wins set doesn't store bare elements. It stores tagged adds:

  • Add an element by recording it with a brand-new, unique tag, such as A1 (replica A's 1st operation) or B3.
  • Remove an element by marking as removed every tag for it that this replica can currently see. Nothing is actually deleted; the tags are crossed out.
  • An element is in the set if it has at least one tag that isn't crossed out.
  • Merge two replicas by taking the union of their tags and the union of their crossed-out tags.

That's where "add wins" comes from. A remove can only cross out tags it has observed. An add that happened concurrently created a tag the remover has never seen, so that tag survives the merge, and so does the element.

Why the replicas always agree

Merging is just set union, applied to the tags and to the crossed-out tags. Union has three properties that make sync order irrelevant:

  • Commutative: merging A into B gives the same result as merging B into A.
  • Associative: with three or more replicas, the grouping of merges doesn't matter.
  • Idempotent: receiving the same update twice changes nothing, so a repeated or duplicated message is harmless.

Because of these properties, any two replicas that have seen the same operations hold the same state, no matter how messages were delayed, reordered or repeated. That guarantee is called strong eventual consistency. You can test it in the playground: sync in any order, as many times as you like, and once both replicas have seen everything, the status says Replicas agree.

The whole thing in code

Here's the whole data structure in Go. The playground above runs the same logic.

type AddWinsSet struct {
	id      string
	counter int
	adds    map[string]string // tag -> element
	removed map[string]bool   // tags that have been crossed out
}

func NewAddWinsSet(replicaID string) *AddWinsSet {
	return &AddWinsSet{
		id:      replicaID,
		adds:    map[string]string{},
		removed: map[string]bool{},
	}
}

func (s *AddWinsSet) Add(element string) {
	s.counter++
	tag := fmt.Sprintf("%s%d", s.id, s.counter) // unique: "A1", "A2", ...
	s.adds[tag] = element
}

func (s *AddWinsSet) Remove(element string) {
	// Cross out only the tags this replica has observed.
	for tag, el := range s.adds {
		if el == element {
			s.removed[tag] = true
		}
	}
}

func (s *AddWinsSet) Has(element string) bool {
	for tag, el := range s.adds {
		if el == element && !s.removed[tag] {
			return true
		}
	}
	return false
}

func (s *AddWinsSet) Merge(other *AddWinsSet) {
	for tag, el := range other.adds {
		s.adds[tag] = el
	}
	for tag := range other.removed {
		s.removed[tag] = true
	}
}

Caveats and variations

  • Tombstones pile up. This simple version never forgets a crossed-out tag, so its state only grows. Production implementations use version vectors ("dots") to track which operations each replica has seen. That lets them throw removed tags away entirely while keeping the same add-wins behaviour.
  • Remove-wins is the mirror image. A remove-wins set resolves the same conflict the other way. Neither is "right": add-wins suits shopping lists and collaborative docs, where losing someone's addition is worse than an item reappearing.
  • Re-adding is a new add. If you remove milk and add it again later, the new add gets a fresh tag, so it isn't affected by the old remove.
