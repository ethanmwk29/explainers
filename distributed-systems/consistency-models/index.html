Consistency models

When a database is replicated, two people can ask the same question and get different answers. A consistency model is the contract that says which answers are allowed.

This page follows the map of consistency models published by Jepsen, the project that tests real distributed databases against the guarantees they claim. It covers the branch for individual operations; the transactional models (serializability, snapshot isolation, and friends) are a separate story.

What a consistency model is

Picture several processes (clients, or threads, or servers) reading and writing a shared set of keys. Each operation takes some time: it's called, then later it returns. The record of every operation, who did it, when it started and ended, and what it returned is a history.

A consistency model is simply a rule for which histories are allowed. A stronger model allows fewer histories, which makes the system easier to reason about but harder to build and slower or less available. A weaker model allows more histories, including some surprising ones, in exchange for speed and availability.

In this page, every key starts at 0, w x=1 means "write 1 to x", and r x→0 means "read x and got 0".

Availability: what you give up

During a network partition, some servers can't talk to others. Jepsen sorts the models by what's still possible then:

  • Totally available: every server that's up can keep answering every request, even cut off from the rest. (Monotonic reads, monotonic writes, writes follow reads.)
  • Sticky available: every server that's up can keep answering, as long as each client keeps talking to the same server. Switch servers and the guarantee can break. (Causal, PRAM, read your writes.)
  • Unavailable: some or all servers must refuse or wait until the partition heals. No model at or above sequential consistency can avoid this. (Sequential, linearizable, strict serializable.)

This is the practical meaning of the CAP theorem: if you want linearizability, a partitioned server sometimes has to say "I can't answer that right now."

    A subtlety about the session guarantees

    The session guarantees are usually combined, and that matters. In Writes out of order, P2 sees y=1 and then x=0. That only counts as seeing P1's writes out of order if P2's second read is at least as up to date as its first, which is monotonic reads' job. With monotonic reads alone or monotonic writes alone, that history can still be explained. Together, it can't. The same goes for Reply before question and writes follow reads. That's why Jepsen describes PRAM as exactly read your writes, monotonic reads, and monotonic writes together.

    How this connects to the other explainers

    • Scuttlebutt gossip has a section placing its guarantees on this map: convergence, monotonic reads if a client sticks to one participant, read your writes for the owner, and not causal.
    • Vector clocks track exactly the "happened before" relation that causal consistency is built on. Systems that offer causal consistency use them (or something like them) to decide when an update is safe to show.
    • The add-wins set offers strong eventual consistency: replicas that have seen the same updates hold the same state. That convergence guarantee isn't one of the boxes on this map, which is about what each read can return along the way.

    Checking a history in practice

    Jepsen's tests run a real database under faults (partitions, crashes, clock skew), record the history of every client operation, then check whether that history is allowed by the model the database claims. Checking linearizability is expensive in general, so real checkers prune the search aggressively. Here's the core idea for a single register in Go: try to find an order that respects real time and makes every read return the latest write. It's tested against an exhaustive check on thousands of random histories.

    // Op is one completed operation on a single register that starts at 0.
type Op struct {
	Start, End int  // when the call began and when it returned
	Write      bool // a write of Value, or a read that returned Value
	Value      int
}

// Linearizable reports whether the ops can be put in one order that
// (1) respects real time: if a returned before b began, a comes first, and
// (2) makes every read return the most recent write before it (or 0).
// This is a brute-force search: fine for small histories. Real checkers,
// like Jepsen's Knossos or Porcupine in Go, prune the search far harder.
func Linearizable(ops []Op) bool {
	placed := make([]bool, len(ops))
	var search func(count, value int) bool
	search = func(count, value int) bool {
		if count == len(ops) {
			return true
		}
		for i, op := range ops {
			if placed[i] || !canGoNext(ops, placed, i) {
				continue
			}
			if !op.Write && op.Value != value {
				continue // this read can't happen now: it would see the wrong value
			}
			next := value
			if op.Write {
				next = op.Value
			}
			placed[i] = true
			if search(count+1, next) {
				return true
			}
			placed[i] = false
		}
		return false
	}
	return search(0, 0)
}

// canGoNext reports whether op i can be next: no unplaced op returned
// before op i began.
func canGoNext(ops []Op, placed []bool, i int) bool {
	for j, o := range ops {
		if !placed[j] && j != i && o.End < ops[i].Start {
			return false
		}
	}
	return true
}

    Interview notes

    How often it comes up: Common in system design interviews, less so in coding rounds. Expect to justify the guarantee you pick for each part of a design.

    Be ready to:

    • Explain linearizable vs. eventually consistent with a concrete stale-read example, and say what linearizability costs (coordination on every operation, unavailability during partitions).
    • Pick a weaker model on purpose: a social feed can tolerate stale reads, but a user should always see their own post (read your writes).
    • Describe how systems provide read your writes and monotonic reads in practice: sticky sessions, reading from the leader, or tracking a version token per client.
    • Explain why causal consistency is often called the strongest model that stays available during partitions (it's sticky available on Jepsen's map).
