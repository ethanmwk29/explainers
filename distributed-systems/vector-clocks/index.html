Explainers/Distributed Systems

Vector clocks

Machines in a distributed system can't agree on what time it is. Vector clocks sidestep the question: instead of asking when something happened, they track who knew what, and that's enough to tell exactly which events could have influenced which.

Based on Leslie Lamport's "Time, Clocks, and the Ordering of Events in a Distributed System" (1978), and on vector clocks as described independently by Colin Fidge and Friedemann Mattern (1988).

No shared clock

On a single machine, ordering events is easy: read the clock. Across machines it isn't. Each machine has its own clock, and those clocks drift: they run slightly fast or slow, and synchronization protocols like NTP can only keep them within some margin, often a few milliseconds and sometimes much worse. Two events a millisecond apart on different machines can easily get timestamps in the wrong order.

For many questions, though, we don't need the real time at all. We need to know whether one event could have affected another. Did the server see the first write before it accepted the second? Was this reply sent after that request arrived? That's a question about causality, and it can be answered without any clock.

Happened before

Model the system as a few processes (machines, threads, replicas) that do three kinds of things, called events: local steps, sending a message, and receiving a message. Lamport defined the happened-before relation, written a → b, with three rules:

  1. Same process: if a and b happen on the same process and a comes first, then a → b.
  2. Messages: if a sends a message and b receives that message, then a → b.
  3. Transitivity: if a → b and b → c, then a → c.

In other words, a → b when you can trace a path from a to b by moving forward along a process's timeline and along messages. If neither a → b nor b → a, the two events are concurrent. Concurrent doesn't mean "at the same moment." It means neither one could have known about the other.

The usual picture is a space-time diagram: one horizontal line per process, time running left to right, and an arrow for each message.

Notice that the diagram's left-to-right position says nothing on its own. A3 is drawn to the right of B3, but A3 didn't happen after B3 in any meaningful sense: no information flowed from B3 to A3.

Lamport clocks: a first attempt

Lamport's paper also introduced a simple way to timestamp events. Each process keeps one counter:

  • Before each local event or send, increment the counter. A send attaches the counter to the message.
  • On receive, set the counter to max(own, message) + 1.

This guarantees that if a → b, then L(a) < L(b). Following a path forward, the counter only goes up. It's enough to build a total order of events that respects causality (sort by counter, break ties by process ID), which is how Lamport used it, for example to implement a distributed mutual-exclusion lock.

But the converse fails: L(a) < L(b) does not mean a → b. Here's the same execution with Lamport timestamps:

Looking only at the numbers 3 and 4, you can't tell whether A3 influenced B3 or whether they're unrelated. Lamport timestamps throw that information away. That matters whenever concurrency is what you're trying to detect. A database that receives two writes to the same key wants to know if the second writer had seen the first (so it's safe to overwrite) or not (so it's a conflict). A single counter can't answer that.

Vector clocks

The fix is to keep one counter per process. With processes A, B and C, every event gets a vector like [2,3,0], with the entries in the order A, B, C. The rules:

  1. Local event or send at process p: increment your own entry, V[p] += 1. A send attaches a copy of the whole vector to the message.
  2. Receive at process p: take the element-wise maximum of your vector and the message's vector, then increment your own entry.

The element-wise maximum just takes the larger value in each position: max([0,1,0], [2,0,0]) = [2,1,0].

What does an entry mean? Entry p of an event's vector counts how many of p's events are in that event's causal history, where the causal history of e is e itself plus every event that happened before it. B2 = [2,2,0] says: "I've been influenced by A's first two events, by B's first two (counting myself), and by nothing from C."

Comparing two vectors

For two events a and b, compare their vectors entry by entry:

  • If every entry of V(a) is ≤ the matching entry of V(b), and at least one is strictly smaller, then V(a) < V(b), and a happened before b.
  • If it's the other way round, b happened before a.
  • If each vector is bigger somewhere, the events are concurrent.

A1 = [1,0,0] and C2 = [2,3,2]: every entry of A1 is smaller or equal, so A1 → C2. A3 = [3,0,0] and B3 = [2,3,0]: A3 is bigger in entry A, B3 is bigger in entry B, so they're concurrent, exactly the case Lamport timestamps got wrong.

The key property: a → b if and only if V(a) < V(b). Unlike Lamport clocks, this works in both directions, so vector clocks detect concurrency exactly.

Why it holds: if a → b, then a's causal history is contained in b's, so no entry can be bigger, and b's own entry counts b itself, which isn't in a's history. Conversely, a process's events in any causal history always form a prefix of its timeline (if you've heard of its 3rd event, you've heard of the first two). So if V(b) counts at least as many of a's process's events as V(a) does, a is among them.

Where vector clocks show up

Detecting conflicting writes

This is the classic use. Amazon's Dynamo attached a vector clock to every version of every object. When a client writes, it sends back the clock of the version it read, so the new version's clock is a descendant of it. When two versions meet, the store compares their clocks. If one is an ancestor of the other, the older one can be thrown away safely. If they're concurrent, neither writer saw the other's write, so the store keeps both versions (Riak calls them siblings) and hands them to the application to merge. Dynamo's example is a shopping cart, where the merge takes the union of the items.

Compare that with last-writer-wins using wall-clock timestamps: one of two concurrent writes silently disappears, and with clock drift, it might even be the one that happened later in real time.

Causal delivery

Some systems promise that if message m1 happened before m2, every process delivers m1 first, so nobody sees a reply before the question. The classic causal broadcast algorithm (Birman, Schiper and Stephenson) uses vectors that count messages broadcast. A process holds back a message from p until it's the next one from p (m.V[p] = V[p] + 1) and the process has already delivered everything the sender had seen from everyone else (m.V[k] ≤ V[k] for every other k).

Debugging distributed traces

Logs from several machines, merged by wall-clock time, can show effects before their causes. If each log line carries a vector timestamp, a tool can reconstruct the real happened-before order and draw a space-time diagram like the one above. ShiViz is one tool that does exactly this.

Relatives elsewhere on this site

  • The add-wins set tags each add with a pair like A3: replica A's 3rd operation. That pair is a single entry's worth of a vector clock, often called a dot. Production versions of the set summarize which dots a replica has seen with a version vector, which lets them drop removed tags instead of keeping them forever.
  • Scuttlebutt gossip exchanges digests that hold, for every participant, the highest version seen from it. That digest is essentially a version vector, and the "send whatever is newer than your entry for r" step is the same entry-by-entry comparison. Merging works the same way too: after an exchange, each entry is the max of the two.

Version vectors and other variants

The names get mixed up in practice, so it helps to separate them:

NameWhat it tracks
Vector clockTimestamps events in an execution. Every local step, send and receive ticks the clock, as in the playground.
Version vectorSummarizes the state of a replica or a version of a piece of data. Only updates tick it, and replicas merge vectors when they sync. Comparing two version vectors tells you whether one replica's state includes the other's or whether they've diverged. Dynamo's "vector clocks" are really used this way.
Dotted version vectorA version vector plus one extra "dot" naming the exact update that created a version. It fixes a problem where many clients writing through the same server produce more siblings than necessary or lose track of which writes were concurrent. Riak adopted them for this reason.
Interval tree clockDesigned for systems where processes come and go. Instead of a fixed list of IDs, participants split and join a shared ID space, so the clock doesn't need a global registry of process names and can shrink when participants retire.

The code

Here's a vector clock in Go. Process IDs are map keys, so a missing entry counts as 0 and the set of processes doesn't need to be fixed up front. Compare returns one of four answers. I tested it against randomly generated executions with late and out-of-order messages, checking that for every pair of events it agrees exactly with happened-before computed by following paths through the event graph, and that Lamport timestamps never contradict happened-before, yet also order many concurrent pairs.

// Order is how two vector timestamps relate.
type Order int

const (
	Equal      Order = iota // the same event (or identical histories)
	Before                  // a happened before b
	After                   // b happened before a
	Concurrent              // neither happened before the other
)

func (o Order) String() string {
	return [...]string{"Equal", "Before", "After", "Concurrent"}[o]
}

// VectorClock maps a process ID to the number of events from that process
// that are known to have happened. A missing entry means 0.
type VectorClock map[string]uint64

// Copy returns an independent copy, safe to attach to a message.
func (vc VectorClock) Copy() VectorClock {
	out := make(VectorClock, len(vc))
	for id, n := range vc {
		out[id] = n
	}
	return out
}

// Merge sets every entry to the larger of the two clocks' values.
func (vc VectorClock) Merge(other VectorClock) {
	for id, n := range other {
		if n > vc[id] {
			vc[id] = n
		}
	}
}

// Compare reports how a relates to b: Before means a happened before b.
func Compare(a, b VectorClock) Order {
	aLess, bLess := false, false // some entry where a < b, or where b < a
	for id, n := range a {
		if n > b[id] {
			bLess = true
		} else if n < b[id] {
			aLess = true
		}
	}
	for id, n := range b {
		if _, ok := a[id]; !ok && n > 0 {
			aLess = true // a's missing entry counts as 0
		}
	}
	switch {
	case aLess && bLess:
		return Concurrent
	case aLess:
		return Before
	case bLess:
		return After
	default:
		return Equal
	}
}

// Process is one participant that keeps a vector clock.
type Process struct {
	ID    string
	Clock VectorClock
}

func NewProcess(id string) *Process {
	return &Process{ID: id, Clock: VectorClock{}}
}

// Local records an internal event and returns its timestamp.
func (p *Process) Local() VectorClock {
	p.Clock[p.ID]++
	return p.Clock.Copy()
}

// Send records a send event. The returned timestamp travels with the message.
func (p *Process) Send() VectorClock {
	return p.Local()
}

// Receive records the receipt of a message carrying timestamp msg: take the
// element-wise max, then count the receive as a new local event.
func (p *Process) Receive(msg VectorClock) VectorClock {
	p.Clock.Merge(msg)
	return p.Local()
}

Typical use: each process calls Local or Send for its own events, and Receive with the clock that came with a message. To check whether two writes conflict, call Compare on their clocks and treat Concurrent as a conflict.

Caveats

  • Size grows with the number of processes. Every message carries one entry per process, and charging each client its own entry can mean thousands of entries. Vector clocks work best with a modest, fairly stable set of participants, such as the replicas of a key, rather than every client.
  • Pruning loses information. To cap the size, systems sometimes drop old entries. Dynamo, for example, removed the oldest entry once a clock passed a size threshold. A dropped entry is treated as 0, which can make a descendant look concurrent with its ancestor (a needless conflict). It can also make a concurrent version look like an ancestor, in which case it gets silently discarded. Dynamo's authors reported that the problem didn't come up in production, but it's a real trade-off.
  • "Happened before" means "could have influenced." B2 counts as after A2 because a message connected them, even if B ignored the message's contents. Vector clocks track potential causality, which is the safe over-approximation.
  • No total order. Concurrent events stay unordered. If you need a single order (for example, to pick a winner), you still need a tie-breaker, such as a Lamport timestamp plus process ID, or an application-level merge.
  • Who gets an entry matters. Entries per server keep vectors small, but then concurrent writes from two clients through the same server look sequential. That's the problem dotted version vectors address.

Interview notes

How often it comes up: Occasionally, in system design interviews, not in coding rounds. The usual setting is "design a key-value store" in the style of Dynamo, Cassandra or Riak, when the conversation reaches replication and conflicting writes.

Be ready to:

  • State the update rules and the comparison rule, and compare two vectors on the spot.
  • Explain why Lamport timestamps can't detect concurrency, and why wall-clock last-writer-wins can lose writes.
  • Walk through what a store does with concurrent versions: keep siblings and return them to the client, or merge them automatically (for example with a CRDT).
  • Discuss the costs: vector size, pruning and its risks, and per-server vs. per-client entries.
